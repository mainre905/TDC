## 0. 전체 흐름

```
Phase 1   Mode 1 (Ring Osc)   →  코드밀도 히스토그램  →  COE 생성 + DNL/INL(SW)
   ↓
Phase 2   Mode 0 (DPS) + 선형 COE   →  BEFORE 전달함수 (무교정)
   ↓
Phase 3   Mode 0 (DPS) + 새 COE     →  AFTER 전달함수 (교정)  + 지터 σ
```

빌드 3회. 각 단계는 **딱 한 가지만** 바뀐다:

| | OPERATION_MODE | 코어 | ROM COE |
|---|---|---|---|
| Phase 1 | **1** (RO) | `tdc_fmcw_core_co` | 선형 (그대로) |
| Phase 2 | **0** (DPS) | `tdc_fmcw_core_co` | 선형 (그대로) |
| Phase 3 | 0 (DPS) | `tdc_fmcw_core_co` | **새 코드밀도 LUT** |

Phase 2는 **ROM 재생성이 필요 없다**(모드만 바꿈). Phase 3은 **모드가 그대로**이고 ROM만 바뀐다.
그래서 Phase 2↔3 비교가 COE 효과만 분리한 통제 비교가 된다.

**Phase 2를 건너뛰면** 논문에 "교정 전/후" 표를 넣을 수 없다. 빌드 1회 값어치가 있다.

## 1. 빌드 전 확인 — 세 가지

### 1-1. clk_wiz_0 의 VCO 주파수 — 가장 중요

시간축 전체가 이 값 하나에 걸려 있다.

```
PHASE_STEP = (VCO 주기) / 56
VCO = 1 GHz 이면  PHASE_STEP = 1000 ps / 56 = 17.857 ps
```

`validate_timestamp.py`의 `PHASE_STEP_PS = 1000.0/56.0`과 반드시 일치해야 한다.

- 기록: VCO = ________ MHz → PHASE_STEP = ________ ps

### 1-2. ROM에 로드된 COE — 오버플로 주의 + 백업 필수

레포의 두 COE는 **둘 다 선형 램프**다. 코드밀도 LUT는 아직 FPGA에 적재된 적이 없다.

| 파일 | 탭당 기울기 | idx 299 값 | 판정 |
|---|---|---|---|
| `python/dummy_rom.coe` | 17.857 ps | **5,339 ps** | **위험** — 5,000 초과 |
| `python/tdc_calib_mode0_rom.coe` | 15.625 ps | 4,672 ps | **안전 — 이걸 쓸 것** |

*근거: 각 파일 `memory_initialization_vector`의 차분 평균. dummy_rom 0,18,36,54,71,… → 17.857 = 5696/319.
mode0_rom 0,16,31,47,62,… → 15.625 = 5000/320. idx 299 값은 기울기×299로 계산 — **유도값**.*

타임스탬프 식은 `timestamp_ps = ts_coarse × 5000 − calibrated_fine_ps[fine_idx]`.
CO 빌드의 유효 탭은 **299개**(`python/co_histo_back.csv` 실측)이므로 `fine_idx`가 299까지 간다.
`dummy_rom.coe`면 idx 280 이상에서 `fine_ps > 5000`이 되어 타임스탬프가 한 주기 뒤로 튄다.
**약 19개 탭이 오염되고, `validate_timestamp.py`의 `(5000 − ts % 5000) % 5000` 복원도 깨진다.**

> ### 백업 먼저 — `Making_COE_Mode_0.py`가 이 파일을 덮어쓴다

> cp tdc_calib_mode0_rom.coe tdc_calib_linear_backup.coe

## 3. 스윕·자극 사양 (RTL에서 읽은 값)

`RTL/phase_shifter.v` — Phase 2·3에서만 사용:
```
DELAY_MAX = 2,000,000 클럭 @ 200 MHz  →  스텝당 체류 10 ms
loop_cnt : 0 → 280 에서 종료          →  281 스텝
281 × 17.857 ps = 5,017.9 ps          →  한 주기(5,000 ps)를 0.36 % 초과, 전 구간 커버
총 스윕 시간 = 281 × 10 ms = 2.81 초
```

`RTL/tdc_test_top.v` hit 생성부 (`sync_cnt` 0~9, `sync_cnt < 2`일 때 high) — Mode 0:
```
hit 주기 = 10 클럭 @ 200 MHz = 50 ns  →  20 MHz, 결정론적
스텝당 히트 수 = 10 ms / 50 ns = 200,000 개
```
**hit이 정확히 10 클럭마다 나온다는 점이 §6 지터 캡처의 전제다.**

## 4. Phase 1 — Mode 1 (Ring Osc) 코드밀도 → COE 생성

### 4-1. 빌드

`OPERATION_MODE = 1` 유지, 224번 줄만 `tdc_fmcw_core_co`로. ROM은 손대지 않는다.

### 4-2. ILA 설정 (히스토그램 캡처)

| 항목 | 값 |
|---|---|
| Capture mode | BASIC |
| Storage qualification | **`probe1` (`readout_active`) == 1** |
| Trigger | `probe1` rising edge |
| Depth | **1024** (320 주소) |
| Radix | `probe4`, `probe5` 모두 **UNSIGNED** |

### 4-3. 캡처 — 3회 (cal 1 + val 2)

리셋 → 히트 충분히 누적(수천만 개) → `readout_active` 자동 스캔 → 캡처 → CSV export.
**리셋해서 히스토그램을 비우고 다시** 3회 반복.

| 캡처 | 파일명 | 용도 |
|---|---|---|
| 1 | `python/ro_cal.csv` | **LUT 생성용 (cal)** |
| 2 | `python/ro_val1.csv` | 평가용 (val) |
| 3 | `python/ro_val2.csv` | 평가용 예비 |

> **cal/val 분리는 필수다.** LUT를 만든 데이터로 그 LUT를 평가하면 자기 일관성을 재는 것이지
> 교정 품질을 재는 게 아니다.

### 4-4. 파이썬 — 어떤 파일을 어떤 순서로

#### ① `python/Histogram.py` — ILA export를 탭 히스토그램으로 변환

**입력 파일명이 하드코딩돼 있다. 매번 고쳐야 한다:**
```python
csv_filepath = os.path.join(script_dir, "co_histo_40_2.csv")   # ← 12번째 줄. 이걸 고칠 것
```
`ro_cal.csv` → 실행 → `ro_val1.csv` → 실행 → `ro_val2.csv` → 실행. **3번 돌린다.**

출력: `tap_histogram_<YYYYMMDD_HHMMSS>.csv` (`Tap_Index`, `Hit_Count`)

#### ② `python/Making_COE_Mode_0.py` — COE 생성

설정 확인 (이미 맞게 돼 있음):
```python
CAL_CSV    = None        # None이면 가장 최근 tap_histogram_*.csv 자동 선택
SOURCE_TAG = "ringosc"   # Mode 1 자극이므로 ringosc 가 맞다
```
**`CAL_CSV = None`이면 "가장 최근 파일"을 잡는다.** cal 파일을 확실히 쓰려면
`CAL_CSV = "tap_histogram_<cal 것>.csv"`로 **명시 지정할 것.**

출력 3개:
- `tdc_calib_ringosc_rom.coe` — 보관용(태그)
- **`tdc_calib_mode0_rom.coe` — 하드웨어 IP가 참조하는 이름. 기존 선형 램프를 덮어쓴다** (§1-2 백업 참조)
- `calib_lut_mode0.png` — LUT 곡선

콘솔에 찍히는 검증값 — **전부 기록할 것**:
```
유효 구간   tap lo ~ hi (bins)
총 히트 H
LUT 범위    0 ~ ? ps  (목표 0~5000)
단조 증가   OK / 역전 존재      ← 역전이면 COE 못 씀
13비트 이내 OK / 초과           ← 초과면 ROM 폭 부족
최대 step(폭) / 최소 step(폭)   ← 최소 0이면 missing code
ROM 라인 수 (필요 320)
```

> **이 스크립트는 DNL/INL을 내지 않는다.** LUT 통계와 곡선만 낸다. DNL/INL은 ③에서 나온다.

#### ③ `python/DNL_INL_codedensity.py` — DNL/INL (교정 전/후)

**cal/val을 직접 지정해야 한다:**
```python
CAL_CSV = "tap_histogram_<cal 것>.csv"    # 22번째 줄
VAL_CSV = "tap_histogram_<val1 것>.csv"   # 23번째 줄
```

출력: BEFORE(raw code density) / AFTER(cal LUT 시간축 위에서 val을 균일 격자로 재비닝)의
**DNL·INL 그래프와 수치.**

- **BEFORE** = 무교정 지연선의 DNL/INL
- **AFTER** = 이 LUT를 적용했을 때 **소프트웨어상 예상되는** DNL/INL

> **AFTER는 아직 계산값이다. FPGA에서 실제로 그렇게 나오는지는 Phase 3에서 확인한다.**

`VAL_CSV`를 val2로 바꿔 한 번 더 돌려 재현성을 볼 것.

## 5. Phase 2 — Mode 0 (DPS) + 선형 COE → BEFORE

### 5-1. 빌드

- 9번 줄 `OPERATION_MODE = 0`
- **ROM은 선형 COE(`tdc_calib_linear_backup.coe`)로 재생성** — Phase 1에서 덮어썼으므로
- 코어는 `tdc_fmcw_core_co` 그대로

### 5-2. 캡처 — 전달함수

| 항목 | 값 |
|---|---|
| Capture mode | BASIC |
| **Storage qualification** | **`probe0` (`capture_trigger`) == 1** |
| Trigger | `probe0 == 1` |
| Depth | **512** (281 스텝) |
| Radix | `probe2`, `probe3` **UNSIGNED** |

`capture_trigger = capture_arm && final_ts_valid`이고 `capture_arm`은 `loop_cnt`가 바뀔 때
장전되어 첫 유효 타임스탬프에서 해제된다. → **스텝당 정확히 1샘플**.

절차: 리셋 → ILA arm → `btn_shift` 1회 → **2.81초 대기** → 281행 확인 → export.

**파일명: `python/before_capture.csv`** ← `validate_timestamp.py`가 이 이름을 기대한다.

3회 반복(`_2`, `_3`)해 재현성 확인.

### 5-3. 파이썬 — `python/validate_timestamp.py`

```python
CAPTURES = [
    ("BEFORE (linear COE)",     "before_capture.csv"),
    ("AFTER (code-density COE)", "after_capture.csv"),
]
```
Phase 2 시점에는 `after_capture.csv`가 없으므로 BEFORE만 처리된다(없는 파일은 무시).

계산 원리 (스크립트 주석 그대로):
```
측정 fine = (5000 − timestamp % 5000) % 5000     ← coarse 성분이 소거됨
참 시간   = loop_cnt × PHASE_STEP_PS (= 17.857 ps)
fine vs loop_cnt 직선 피팅 → 잔차 = INL, 스텝 간 차분 = DNL
```

이게 **진짜 시간 눈금을 대고 잰 DNL/INL**이다. Phase 1 ③의 코드밀도 DNL/INL과 대조할 것.
두 방법이 같은 지연선을 다른 원리로 재므로, 일치하면 양쪽 다 신뢰할 수 있다.

## 6. Phase 3 — Mode 0 (DPS) + 새 COE → AFTER + 지터

### 6-1. 빌드

- `OPERATION_MODE = 0` 유지
- **ROM만 Phase 1이 만든 `tdc_calib_mode0_rom.coe`(코드밀도 LUT)로 재생성**
- 그 외 전부 동일 → **COE 효과만 분리된 통제 비교**

### 6-2. 캡처 A — 전달함수 (AFTER)

§5-2와 **완전히 같은 ILA 설정**. 파일명만 다름.

**파일명: `python/after_capture.csv`**, 3회 반복.

### 6-3. 캡처 B — Mode 0 히스토그램 (LUT 유효성 교차확인)

§4-2와 같은 ILA 설정(`probe1` qual, depth 1024). 파일명 `python/mode0_histo_1.csv`.

`tdc_histogram`은 **교정 전 raw `aligned_fine_idx`**를 누적하므로 COE와 무관하다.
따라서 Phase 1의 `ro_cal.csv`와 직접 비교할 수 있다.

**Mode 1(RO)과 Mode 0(DPS)은 클럭이 다르다** — `clk_200_fixed` vs `clk_200_shifted`.
두 히스토그램이 다르면 **RO로 만든 LUT를 DPS 빌드에 쓴 것이 부적절**했다는 뜻이므로,
그때는 Mode 0 히스토그램으로 LUT를 다시 만들어야 한다. **이 확인을 빼면 안 된다.**

파이썬: `Histogram.py`(파일명 수정) → `DNL_INL_codedensity.py`
(`CAL_CSV`=Phase 1 cal, `VAL_CSV`=이번 mode0 히스토그램)

### 6-4. 캡처 C — 지터 σ (single-shot precision)

**원리**: 위상 스텝을 하나 고정하면 hit–클럭 간격이 고정된다. 잡음이 없다면 200,000번 모두
같은 탭에 떨어져야 한다. 실제 흩어짐의 표준편차가 σ다.
**외부 function generator가 하는 일을 MMCM이 온칩으로 대신한다.**

| 항목 | 값 |
|---|---|
| Capture mode | BASIC |
| **Storage qualification** | **없음** (모든 사이클 저장) |
| **Trigger** | **`probe2` (`current_loop_cnt`) == N** |
| Depth | **4096 이상** |
| Radix | `probe2`, `probe3` **UNSIGNED** |

qual을 안 거는 이유: `final_ts_valid`가 ILA 프로브에 없다. 대신 hit이 정확히 10 클럭마다
결정론적으로 나오므로 4096 사이클 안에 히트가 약 **410개** 들어 있고 파이썬에서 뽑을 수 있다.
410 샘플이면 σ 추정의 상대오차가 1/√(2·410) ≈ 3.5 %.

| 캡처 | N | 트리거까지 | 파일명 |
|---|---|---|---|
| C-1 | 40 | 0.4 s | `python/mode0_jit_040.csv` |
| C-2 | 100 | 1.0 s | `python/mode0_jit_100.csv` |
| C-3 | 160 | 1.6 s | `python/mode0_jit_160.csv` |
| C-4 | 220 | 2.2 s | `python/mode0_jit_220.csv` |

**파이썬: 기존 스크립트 없음. 신규 작성 필요** — CSV를 주시면 만들겠습니다.
(하는 일: 10클럭 주기로 히트 추출 → `(5000 − ts % 5000) % 5000`로 fine 복원 → 표준편차)

## 8. 기대값 — 이 값들과 대조할 것

`python/co_histo_back.csv` (2026-08-13, CO 빌드, 유효탭 299, 총 히트 187,096,643)에서 유도.
`w[i]` = 탭 폭 = `h[i]/H × 5000 ps`, `p[i] = h[i]/H`.

| 양 | 값 | 계산식 | 종류 |
|---|---|---|---|
| LSB (산술평균 탭 폭) | **16.722 ps** | 5000 / 299 | 유도 |
| 히트가중 평균 탭 폭 | 24.138 ps | Σ w[i]·p[i] | 유도 |
| **σ 기대값 (양자화 한계)** | **7.87 ps** | √( Σ w[i]²·p[i] / 12 ) | 유도 |
| 탭이 균일했다면 | 4.83 ps | LSB / √12 | 유도 |
| 최대 탭 폭 | 86.6 ps | max w[i] | 측정 |
| 코드밀도 INL p-p (무교정) | 99.0 ps | 같은 파일 | 유도 |

### 판정 기준

- **σ(N) 7~9 ps** → 양자화 한계 도달. 지연선 자체 잡음은 무시할 수준.
- **σ(N) 12 ps 이상** → 초과분이 실제 잡음. 원인 추적 필요.
- **σ(N)이 그 지점 탭 폭을 따라 변해야 한다** (양자화 잡음 = 탭폭/√12). 안 따라가면 탭 폭과
  무관한 잡음원이 있다는 뜻이고, 그것도 결과다.
- **AFTER의 INL이 BEFORE보다 확실히 작아야 한다.** 안 줄면 LUT가 틀렸거나 §6-3의
  Mode 1↔Mode 0 히스토그램 불일치를 의심할 것.
- **`validate_timestamp.py` 직선 기울기가 1.0 ± 0.01** 밖이면 `PHASE_STEP_PS`나 VCO 설정을 의심.

## 11. 이번 평가에서 하지 않는 것 (범위 명시)

- **2채널 차분법** — 지연선을 하나 더 만들어야 하므로 범위 밖. **단일 체인으로 간다.**
- **외부 신호원(STM32 / function generator) 검증** — Zybo는 50 Ω 입력이 없어 PMOD 경유 시
  반사·슬루 저하로 time walk가 생긴다. STM32 출력 지터(일반 사양 20~50 ps, **미측정**)가
  이 TDC의 σ(≈ 8 ps)보다 커서 TDC가 아니라 STM32를 재게 된다. 별도 과제로 분리.
- **절대 이득의 독립 검증** — 코드밀도 정규화(`w[i] = h[i]/H × 5000 ps`)가 지연선 전체를
  클럭 주기에 앵커시키므로, 이득은 **측정이 아니라 정의**다. 논문에 그렇게 명시해야 한다.
- **온도 실험** — `python/co_temp/`(2026-08-06)는 **현재 빌드와 다른 빌드**다
  (유효탭 284 vs 299, 탭 폭 상관 r = 0.55). 한 표에 섞지 말 것.
- **thermometer 도착 순서** — `dbg_thermo` 프로브를 붙이면 `final_timestamp_ps`가 죽어
  타임스탬프 데이터패스 전체가 최적화로 사라지고 배치가 바뀐다. 즉 **측정 빌드와 다른 회로**가
  된다 (2026-08-13 확인). 이번 평가와 분리한다.
