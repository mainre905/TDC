## 1. 용어 — 이 보고서에서 쓰는 말

- **탭(눈금)**: 지연선에 새겨진 320개 칸 중 하나. TDC 가 "몇 번 칸에 멈췄다"고 보고하는 그 번호.
- **눈금표(LUT)**: "몇 번 칸이 몇 ps 위치인가"를 정리한 표. 지금 회사가 겪는 것은 이 표를 두 가지 방법으로 만든 결과가 다르다는 문제입니다.
- **Mode 1(코드밀도)**: 히트를 무작위로 수억 발 뿌려서, 어느 칸에 많이 떨어지는지 세어 표를 만드는 방법. 참 시간을 몰라도 됩니다.
- **Mode 0(위상 스윕)**: MMCM 이라는 회로로 신호 위상을 17.857 ps 씩 280번 움직입니다. 이 위상값이 **참 시간**이므로, 보고된 값과 직접 비교해 표가 맞는지 검증할 수 있습니다.
- **경계 불연속**: 클럭 한 바퀴(5000 ps)를 넘는 순간 보고값이 매끄럽게 안 이어지고 튀는 양. 표의 총합이 정확히 5000 ps 가 아니면 생깁니다. 0 이어야 정상.
- **양자화 한계**: 한 칸 안 어디에 떨어졌는지는 알 수 없으므로, 아무리 표를 정교하게 만들어도 남는 최소 오차.

## 2. 배경 — 이 조사가 왜 시작됐나

## 4. 진짜 원인 — 시계 한 바퀴가 320칸을 다 못 돈다

### 4-1. 발견

**측정(measured)**: Mode 0(위상 스윕)이 실제로 도달하는 칸은 최대 295~296번입니다. 그런데 Mode 1(링오실레이터)은 299번 칸까지 히트를 쌓습니다.

**설명(사용자 확인, 2026-08-24 대화)**: 위상 스윕은 5000 ps(클럭 한 바퀴) 딱 그만큼만 움직입니다(`280 스텝 × 17.857 ps = 5000 ps`). **그런데 지연선 320칸을 전부 지나가는 데 걸리는 실제 시간이 5000 ps 보다 깁니다.** 그래서 위상 스윕은 애초에 지연선 끝부분(약 293번 너머)에 닿을 수가 없습니다 — 이건 결함이 아니라 이 측정 방법의 구조적 한계입니다.

반면 Mode 1 은 히트가 계속 반복됩니다. 아주 가끔(온도·전원 요동 등으로) 캐리가 평소보다 빨리 도는 순간이 걸리면, 294~299번 칸까지 닿을 수 있습니다. **그 "아주 가끔"을 히트 수억 발 중에서 잡아낸 것**입니다.

### 4-2. 왜 이게 LUT 을 망가뜨리나 — 자 비유

지연선은 320칸짜리 자입니다. Mode 1 이 잰 "칸 폭"을 가지고, **5000 ps 를 칸들에 나눠주는 게 LUT 을 만드는 일**입니다.

지금 스크립트(`Making_COE_Mode_0.py`)는 "히트가 있는 칸이면 전부 포함"해서, 5000 ps 를 298개 칸에 나눴습니다. 그런데 5000 ps 안에 정상적으로 들어가는 칸은 293개뿐입니다.

**294~299번 칸은 정말로는 그 5000 ps 안에 없는 칸인데, 거기에도 몫을 떼준 것입니다.** 그만큼 나머지 293개 칸이 실제보다 조금씩 좁게 배정됐습니다.

**표는 누적됩니다.** 칸 하나하나는 0.1~0.5 % 정도만 틀려도, 100번째 칸 근처에서는 그게 다 더해져 몇 ps, 290번째 근처에서는 5 ps 넘게 벌어집니다. 이게 실측 INL 오차가 나빠진 이유입니다.

**"모든 칸이 똑같다"고 가정하는 무교정 방식은 오히려 이 문제가 없습니다.** 칸마다 크게 틀리지만, 어떤 칸은 너무 크게 어떤 칸은 너무 작게 잡아서 서로 상쇄되기 때문입니다. 그래서 정교한 표가 대충 가정보다 나쁜, 얼핏 말이 안 되는 결과가 나왔습니다.

### 4-3. 검증 — 경계 불연속으로 확인

**"5000 ps 가 정확히 몇 번 칸까지인가"**를 실측으로 쓸어봤습니다. 몇 번 칸까지 나눠줬을 때 클럭 경계에서 튀는 양(경계 불연속)이 0 이 되는지 봤습니다.

**유도(derived), 출처 `data/Test_20260823/mode0_tf_1~3.csv`, 방법: 각 스텝 48샘플(16×3캡처) 평균 → 참 시각(스텝×17.857 ps)에 직선 적합 → 잔차의 rms**:

| 몇 번 칸까지 나눴나 | 경계 불연속 | INL 오차 rms |
|---|---|---|
| 299칸까지 (현재 스크립트) | −26.5 ps | 19.93 ps |
| 296칸까지 | −14.3 ps | 13.62 ps |
| **293칸까지** | **+0.6 ps ← 0에 가장 가까움** | **10.00 ps ← 최소** |
| 290칸까지 | +12.3 ps | 12.92 ps |

**경계 불연속이 0 이 되는 지점과 INL 오차가 최소가 되는 지점이 정확히 일치합니다.** 경계 불연속은 INL 을 보지 않고도 잴 수 있는 독립적인 값이라, 이 일치는 우연이 아닙니다. **"5000 ps 는 293번 칸까지"**라는 결론이 확인됐습니다.

## 5. 새 눈금표 — 293칸으로 다시 만들기

### 5-1. 무엇을 했나

**Mode 1 히스토그램(`ro_cal.csv`)만 사용**해서, 5000 ps 를 293칸(탭 2~294)에 나눈 새 눈금표를 만들었습니다. Mode 0 데이터는 표를 만드는 데 쓰지 않았습니다 — 293 이라는 칸 수는 §4-3 에서 이미 확인된 값을 그대로 적용했을 뿐입니다.

> **이 새 눈금표는 아직 파이썬 계산 결과일 뿐, FPGA 에 넣어본 적이 없습니다.** 저장소 파일도 바꾸지 않았고 스크래치패드에만 저장돼 있습니다.

### 5-2. Mode 1 안에서 다시 확인 — 여전히 정상

**측정 기반 계산(derived), `ro_val1.csv`/`ro_val2.csv` 로 검증**:

| | 옛 표 (298칸) | 새 표 (293칸) |
|---|---|---|
| ro_val1 오차 | 5.64 ps | 5.72 ps |
| ro_val2 오차 | 5.85 ps | 5.81 ps |

**거의 차이가 없습니다.** 이는 예상된 결과입니다 — 이 검증(DNL)은 칸들의 상대적 비율만 재기 때문에, 몇 개 칸을 자르든 안쪽 칸들의 비율은 거의 안 바뀝니다. **바로 이래서 Mode 1 검증만으로는 이 문제가 안 보였습니다.**

### 5-3. Mode 0 실측 데이터에 소프트웨어로 대입 — 여기서 갈림

BEFORE 캡처(등간격 표를 넣고 잰 실측)는 표 값이 전부 달라서, 어느 히트가 몇 번 칸에서 왔는지 거꾸로 찾아낼 수 있습니다. 그 칸 번호에 새 눈금표 값을 대입해, **실측과 완전히 같은 계산 방법**으로 오차를 다시 쟀습니다.

**항등 검증부터**: 원래 표(선형)를 그대로 대입하면 15.68 ps 가 나와야 합니다 — **정확히 일치**했습니다. 이 계산 방법이 실측과 같다는 뜻입니다.

**유도(derived), 출처 `data/Test_20260823/mode0_tf_1~3.csv` + 소프트웨어 계산, 계산 방법은 §4-3 과 동일**:

| 대입한 표 | INL 오차 rms | 경계 불연속 |
|---|---|---|
| 등간격 (무교정, 실측 대응) | 15.68 ps | −10.7 ps |
| 옛 눈금표 298칸 (실측 대응 19.96 ps 와 19.93 로 거의 일치 — 계산 신뢰성 확인) | 19.93 ps | −26.5 ps |
| **새 눈금표 293칸** | **10.00 ps** | **+0.6 ps** |

**293칸으로 자른 표를 쓰면, 무교정(15.68)보다도 확실히 좋아집니다.** 개선폭은 −36 %입니다.

## 6. 아직 확실하지 않은 것

### 6-1. 남은 오차 약 4.7 ps

이 지연선을 **완벽히** 재면(위상 스윕 자체를 참 눈금표로 써서, 자기 데이터로 자기를 검증) 오차 rms 는 5.30 ps 까지 내려갑니다(§4-3 검증 과정에서 함께 확인, 경계 불연속도 정확히 0). 293칸 새 표의 10.00 ps 와 비교하면 **약 4.7 ps 가 아직 설명되지 않습니다.**

즉 **293칸으로 자른 것만으로 문제가 다 풀린 게 아니라, Mode 1(링오실레이터)이 잰 칸 폭 자체가 Mode 0(위상 스윕)이 실제로 겪는 칸 폭과 완전히 같지는 않습니다.** 왜 다른지는 아직 원인을 모릅니다.

### 6-2. 양자화 한계와의 관계

**유도(derived)**, 293칸 기준 재계산: 한 칸 안 위치를 모르는 데서 오는 최소 오차(양자화 한계)는 **7.99 ps** 입니다(298칸 기준으로는 7.82 ps — 거의 같음). 새 표의 10.00 ps 는 이 한계보다 큽니다. 즉 이 지연선을 아무리 정확히 재도 7.99 ps 밑으로는 못 내려간다는 뜻이고, 293칸 표(10.00)는 그 한계에 어느 정도 근접했지만 아직 여유가 있습니다.

### 6-3. Mode 1이 왜 299번까지 보는지

294~299번 칸에 대한 히트는 캐리가 "우연히 빨리 도는 순간"에만 잡힌다는 것이 지금까지의 설명(가설)입니다. **넷리스트나 타이밍 리포트로 실제 확인한 바는 없습니다.**

### 6-4. RTL 수정(§3)을 유지할지

클럭을 맞춘 것 자체는 CARRY4 안 위치 무늬(§3-2)를 없앴다는 확실한 효과가 있었지만, 정작 사용자가 원한 문제(LUT 적용 시 오히려 나빠짐)는 클럭과 무관했던 것으로 드러났습니다. 이 RTL 변경을 남겨둘지 되돌릴지는 아직 결정하지 않았습니다.
