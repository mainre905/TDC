## 0. 용어 정의

이 리포트에서 쓰는 말을 먼저 정의한다. 이하 본문은 여기 정의된 이름만 사용한다.

### 0-1. 하드웨어 쪽

| 용어 | 정의 |
|---|---|
| **탭 (tap)** | CARRY4 체인 위의 관측점. 총 320개(80단 × 4). hit 신호가 체인을 타고 달리다 클럭이 끊는 순간 "몇 번째 탭까지 갔는지"가 측정값이 된다 |
| **fine index** | 위에서 나온 탭 번호. `popcount`(1이 된 탭 개수)로 구한다 |
| **O 탭 / CO 탭** | CARRY4의 어느 출력을 관측점으로 쓰는가. **O**는 XOR 게이트 출력, **CO**는 캐리(MUXCY) 출력. 오늘 O → CO로 바꿨다 |
| **유효 탭 구간** | 체인이 클럭 1주기(5000 ps)보다 길어서 뒤쪽 탭에는 캐리가 도달하지 못한다. 실제로 hit이 쌓이는 구간만 유효로 본다. 판정 기준은 `Making_COE_Mode_0.py`의 `EDGE_TRIM_FRAC = 0.05`(평균 hit의 5 % 미만인 양 끝단 제거) |

### 0-2. 측정과 계산

| 용어 | 정의 | 산출식 |
|---|---|---|
| **히스토그램** | 탭별 hit 누적 횟수 `h[i]`. ILA로 읽어낸 원자료 | — |
| **코드 밀도 (code density)** | 클럭과 무상관한 랜덤 hit을 수천만 번 때리면 **넓은 탭에 그만큼 자주 떨어진다**는 성질로 탭 폭을 구하는 방법 | — |
| **폭 (width)** | 탭 하나가 담당하는 시간 구간 [ps] | `w[i] = h[i]/H × 5000`, `H` = 유효 구간의 `h` 합 |
| **LUT** | **탭 번호 → 시간 변환표.** 320줄. 폭을 앞에서부터 누적한 것. `.coe` 파일로 ROM에 굽는다. 리포트 전체에서 "표"·"교정표"라 부르지 않고 **LUT로 통일** | `LUT[i] = (5000/H) × (Σ_{k<i} h[k] + h[i]/2)`, bin 중심 |
| **LSB** | 평균 탭 폭 [ps]. 해상도 | `LSB = mean(w)` |
| **DNL** | 탭 하나가 이상값(LSB)에서 얼마나 벗어났나 [LSB 단위] | `DNL[i] = w[i]/LSB − 1` |
| **INL p-p** | DNL을 누적한 값의 최대−최소. **체인을 따라 오차가 얼마나 쌓이는가** = 선형성 | `INL = cumsum(DNL)`, `p-p = max − min` |

### 0-4. 오차를 요약하는 방법

40 °C LUT를 80 °C에서 쓰면 탭마다 오차가 하나씩, 총 270개가 나온다. 이를 숫자 하나로 줄이는 방법이 두 가지다.

| 용어 | 정의 | 답하는 질문 |
|---|---|---|
| **잔차 (residual)** | LUT가 답한 시간 − 진짜 시간 [ps]. 탭마다 하나씩 | — |
| **최대 잔차** | 270개 중 절댓값이 가장 큰 것 | "재수 없으면 얼마나 틀리나" |
| **가중 RMS** | 270개를 평균내되, **각 탭의 오차에 그 탭의 폭을 곱해서** 평균. 폭 = hit이 떨어질 확률이기 때문 | "실제로 측정하면 평균 얼마나 틀리나" |
| **노이즈 바닥** | **같은 온도** 반복 캡처끼리 위와 똑같은 절차를 적용했을 때 나오는 값. 측정 자체의 흔들림 | "이보다 작으면 의미 없다" |

> **가중이 무엇을 가중하는가:** 탭 폭이 76.68 ps인 탭 1에는 폭 1.03 ps인 탭 80보다 hit이 76배 자주 떨어진다. 270개 오차를 똑같이 1표씩 세면 거의 맞지 않는 탭이 과대 반영된다. 그래서 폭으로 가중한다. **LUT나 COE를 건드리는 것이 아니라, 오차를 요약하는 방식일 뿐이다.**

## 1. 오늘의 결론

1. **CO 탭 전환으로 INL이 −37.8 % 개선됐고, 빌드 통제 실험으로 확정했다.** 같은 날 O·CO를 각각 재빌드해 비교한 결과 `155.8 → 96.8 ps`. 두 분포가 전혀 겹치지 않는다(O 153.5~183.8, CO 92.7~98.6 ps). (§2-7)
2. **★ CO 빌드는 온도 보정이 거의 필요 없다.** 40 °C 변화에 무보정 드리프트가 **8.3 ps**(O는 69.7 ps)이고, 가중 RMS 3.7 ps는 **TDC 자체 양자화 잡음 5.3 ps보다 작다.** 단발 측정에서는 보정이 무의미하다. (§3-5)
3. **⚠️ 그래서 이중 체인 무정지 재교정 구조는 전제를 잃었다.** §3-3의 42.7 ps는 온도 특성이 아니라 **잘못된 탭 선택의 결과**였다. 논문 방향 재검토가 필요하다. (§3-5)
4. **대신 새 주장이 나왔다** — "어느 CARRY4 출력을 탭으로 쓰느냐가 온도 안정성을 결정한다." Carra *TNS* 2018은 C/S 16조합을 비교했으나 **상온 정적 DNL만** 봤고, 온도 안정성 비교는 로컬 27편에 없다. (§5-2)
5. **★ Thermometer code 실측으로 CARRY4 내부 구조를 확정했다.** 도착 순서는 `CO[1]→CO[3]→CO[2]→CO[0]`이며 **무작위 bubble이 아니라 고정된 순열**이다(가능한 14패턴 중 3개만 출현). `CO[3]`이 `CO[0]`보다 먼저 도착하므로 **7-series CARRY4는 리플이 아니라 look-ahead 구조**임이 실측으로 확인됐다. (§2-8)
6. **bin↔물리 소자 대응이 확정되어, CARRY4 내부 네 구간의 온도계수를 처음으로 분리했다** — `−4202` ~ `+2795` ppm/°C로 약 7000 ppm/°C 벌어지는데 단당 합계는 `−3` ppm/°C다. **딜레이라인은 전체가 늘거나 주는 게 아니라 CARRY4 내부에서 시간이 재분배된다.** 5개 온도점 전부 단조, 반복 산포의 7~21배. (§3-6)
7. **`tap%4` 접근은 조건부로 되살아났다.** 접었던 이유(bin↔물리 대응 불명, 지표 A의 좁은-탭 지배)가 §2-8·§4-1로 해소됐다. (§4)
8. **CO 개선의 메커니즘은 여전히 모른다.** 전환 근거로 삼았던 단조성 가설은 §2-8에서 명확히 부정됐다(CO도 비단조). 결과만 확실하다.

## 2. CO 탭 전환

### 2-1. 무엇이 문제였나 — Vivado 타이밍 arc

**무슨 데이터로:** Vivado Tcl `get_timing_arcs -of_objects [get_cells ... CARRY_CHAIN[16] ... u_carry4]`, speed file `-1 PRODUCTION 1.12`.
**어떻게:** CI 핀에서 출발하는 arc의 `DELAY_FAST_MIN_RISE` 속성. 단위 ns → ps 변환(×1000), 행은 값 오름차순 정렬(원 출력 순서와 다름).
**라벨: 모델값** — 실측이 아니라 벤더 STA 모델.

| arc | fast_min [ps] |
|---|---|
| CI → O[0] | 53 |
| CI → O[2] | 66 |
| CI → O[1] | 89 |
| CI → O[3] | 91 |
| **CI → CO[3]** | **40** |

**의미 두 가지** (같은 코너 안에서의 비교이므로 유효):

1. **캐리가 4단을 전부 통과하는 데 40 ps인데, XOR 출력 하나 나오는 데 53 ps 걸린다.** 즉 O 탭이 보는 것은 캐리가 아니라 "캐리 + XOR 경로"이고, 그 XOR 경로가 캐리 체인 전체보다 무겁다.
2. **O의 도착 순서가 인덱스 순서가 아니다** (`0, 2, 1, 3`).

**2번이 왜 문제인가:** `popcount`는 "1이 된 탭의 개수"를 센다. 따라서 **히스토그램의 bin 번호는 물리적 탭 번호가 아니라 "도착 순서 등수"**다. 도착 순서가 뒤섞이면 bin ↔ 탭 대응에 permutation이 끼고, 그 순열을 모르면 어느 bin이 어느 물리 구조에 해당하는지 말할 수 없다.

**모델의 한계:** 같은 arc가 fast_min 91 ps ~ slow_max 315 ps로 3.5배 벌어진다. 실측 CARRY4 단당 스팬은 71 ps다. STA용 코너 묶음이라 ps 단위 판정에 쓸 정밀도가 아니다.

### 2-2. 무엇을 바꿨나 — `RTL/tdc_fmcw_core_co.v` (신규)

원본 `tdc_fmcw_core.v`는 손대지 않고 사본을 만들었다. 변경점 3곳:

| 위치 | 변경 |
|---|---|
| `u_ff_0..3`의 `.D` | `carry_o[...]` → `carry_co[...]` |
| 신규 wire | `taps_eff = ~taps_sampled_d1` |
| 트리거·popcount | `taps_sampled_d1[...]` → `taps_eff[...]` |

**극성 반전이 필요한 이유:** `S=4'b1111`이므로 `O[j] = 1 XOR carry = ~carry`, `CO[j] = carry`로 논리가 반대다. 원본(O 탭)은 hit 하강 시 탭이 0→1로 전파되어 `popcount` = 지나간 탭 수였는데, CO 탭은 1→0으로 전파되어 `popcount` = **아직 안 지나간** 탭 수가 된다.

**왜 FF 뒤에서 반전하는가:** `.D(~carry_co[...])`로 탭 경로에 인버터를 넣으면 LUT1이 끼어들어 **CO로 바꾼 이유(XOR 경로 제거)가 사라진다.** 샘플링 FF 뒤에서 반전하면 뒤따르는 popcount LUT에 흡수되어 추가 지연이 0이다. `taps_sampled_d1` 자체도 반전하지 않는다 — `tdc.xdc`가 이 레지스터를 `SLICE_X43Y*`에 고정해 두었고 중간에 LUT가 들어가면 배치가 깨진다.

**빌드:** `tdc_test_top.v:218`의 `tdc_fmcw_core` → `tdc_fmcw_core_co` 한 단어. 포트와 내부 인스턴스 이름을 원본과 동일하게 유지했으므로 **`tdc.xdc`의 LOC/BEL 제약 2000여 줄이 수정 없이 적용된다.**

### 2-3. 합성 후 검증 (구현 완료 후, 비트스트림 전)

**(a) FF가 실제로 CO를 받는지 — ✅**

```tcl
foreach j {0 1 2 3} {
  set ff [get_cells -hier -filter "NAME =~ *CARRY_CHAIN?16?.u_ff_$j"]
  set d  [get_pins -of_objects $ff -filter {REF_PIN_NAME == D}]
  puts [get_pins -leaf -of_objects [get_nets -of_objects $d] -filter {DIRECTION == OUT}]
}
```
→ 4개 모두 `u_tdc/CARRY_CHAIN[16].STAGE_N.u_carry4/CO[j]`

> 대괄호를 `?16?`으로 우회하는 이유: Vivado 필터의 `=~`는 glob이라 `[16]`이 "1 또는 6 한 글자"인 문자클래스로 해석된다. 이것 때문에 처음에 `No pins matched`가 났다.

**(b) 배치 — ✅** 4개 FF + CARRY4 전부 `SLICE_X42Y16`, BEL은 `AFF/BFF/CFF/DFF`. 원본과 동일.

**(c) CI→CO arc — ❌ 기대와 불일치**

원본에는 CO[0..2]가 미연결이라 arc가 없었는데, CO 빌드에서 새로 생겼다. **원본에서는 얻을 수 없던 데이터다.**

| arc | fast_min [ps] |
|---|---|
| CI → CO[3] | **40** |
| CI → CO[1] | 45 |
| CI → CO[2] | 64 |
| CI → CO[0] | **73** |

**단조 증가가 아니다.** 직렬 캐리라면 `CO[0] < CO[1] < CO[2] < CO[3]`이어야 하는데 정반대다. 가능한 해석은 7-series CARRY4가 단순 4단 리플이 아니라 **캐리 look-ahead** 구조여서 체인 연결용 `CO[3]`만 빠른 경로로 계산되는 경우다. 사실이라면 **CO도 O처럼 도착 순서가 섞이며, 전환 근거였던 "단조성 보장"은 성립하지 않는다.**

### 2-4. 측정 조건

| 항목 | 값 | 이유 |
|---|---|---|
| 모드 | **Mode 1 (Ring Oscillator)** | 형상 측정에는 클럭과 무상관한 균일 자극이 필요. Mode 0(DPS)은 위상 스텝 17.857 ps ≈ 탭 폭 1개라 개별 bin 분해 불가(재현성 실측 0.42 vs RO 0.06) |
| ILA 트리거 | `probe1 (readout_active) == 1` | 리드아웃 구간만 캡처 |
| Trigger position | 0 | |

### 2-8. ★★ Thermometer code 실측 — bubble 확인과 bin↔물리소자 대응 확정

**왜 필요했나:** 히스토그램은 `popcount`(1이 된 탭의 개수)만 기록한다. popcount는 정의상 bubble에 면역이라 개수는 맞게 나오고, 따라서 **히스토그램만으로는 탭이 순서대로 도착했는지 알 수 없다.** §2-3c에서 Vivado arc가 CO 도착 순서를 비단조라고 했지만 그건 모델값이었다. 원시 thermometer code를 직접 떠서 확인했다.

**무슨 데이터로:** `python/thermo_1csv.ila.csv` — 임시 RTL(`dbg_thermo`/`dbg_valid`, §RTL 주석 참조)로 **스냅샷 시점의 탭 64~111 원시 상태 48비트**를 캡처. storage qualification `dbg_valid==1`로 프론트가 창 안에 있는 샘플만 저장. **1024샘플 전부 유효**, 고유 패턴 47종.

> ⚠️ 파싱 주의: pandas가 이진 문자열을 정수로 읽어 앞자리 0을 지운다. `dtype=str` + `zfill(48)` 필요.

#### 결과 1 — 무작위 bubble이 아니라 고정된 구조적 순열

partial 그룹(4탭이 전부 1도 전부 0도 아닌 CARRY4)의 패턴이 **가능한 14가지 중 3가지만** 나타났다.

| (CO0,CO1,CO2,CO3) | 횟수 | 비율 | 통과한 것 |
|---|---|---|---|
| `(0,1,0,0)` | 443 | 55.2 % | CO[1] |
| `(0,1,0,1)` | 95 | 11.8 % | CO[1], CO[3] |
| `(0,1,1,1)` | 264 | 32.9 % | CO[1], CO[3], CO[2] |

단조 패턴(`1000`/`1100`/`1110`)은 **0개**. 그리고 0→1 전이가 `%4==1`(89.4 %)과 `%4==3`(10.6 %)에만 나타나고 `%4==0`·`%4==2`에는 **한 번도** 없다. **무작위였다면 47개 위치에 흩어져야 하므로 metastability가 아니다.**

#### 결과 2 — 실측 도착 순서

```
CO[1]  →  CO[3]  →  CO[2]  →  CO[0]
```

CO[1]은 모든 partial 패턴에 등장(100 %)하므로 **첫 번째**. CO[0]은 어디에도 없는데(0 %), CO[0]이 켜지는 순간 `1111`이 되어 partial이 아니게 되기 때문이다 — 즉 **마지막**.

**arc 모델 대비:** 모델은 `CO[3](40) < CO[1](45) < CO[2](64) < CO[0](73)` ps였다. **3·4위(CO[2], CO[0])는 정확히 일치**하고, 뒤바뀐 CO[1]/CO[3]은 모델에서 5 ps 차이라 코너 모델의 분해능 밖이다.

#### 결과 3 — ★ look-ahead 구조가 실측으로 확인됨

직렬 리플 체인이라면 캐리가 `CO[0] → CO[1] → CO[2] → CO[3]` 순으로 지나가야 한다. **그런데 CO[3]이 CO[0]보다 먼저 도착한다.** 물리적으로 불가능한 조합이므로:

> **7-series CARRY4는 4단 리플이 아니라 캐리 look-ahead 구조이고, 체인 연결용 CO[3]은 CI에서 직접 빠른 경로로 생성된다.**

§2-3c에서 **가설**로 제기한 것이 실측으로 확정됐다.

#### 결과 4 — ★★ bin ↔ 물리 소자 대응 확정

`popcount = n`은 "n개가 통과했다"이므로 bin *n*은 **n번째와 n+1번째 도착 사이의 구간**이다. 위 도착 순서를 적용하면:

| bin | 물리 구간 |
|---|---|
| `%4==0` | **CO[0] → 다음단 CO[1]** ← CARRY4 간 배선 포함 |
| `%4==1` | CO[1] → CO[3] |
| `%4==2` | CO[3] → CO[2] |
| `%4==3` | CO[2] → CO[0] |

**독립 검증:** thermometer의 체류 시간 비율로 구간 폭을 추정해 히스토그램과 대조하면 **네 구간 모두 ±1.9 ps 안에서 일치**한다.

| 물리 구간 | thermo 체류(1024샘플) | histogram(3.3e7 hit) | 차이 |
|---|---|---|---|
| CO[0] → 다음단 CO[1] | 18.68 ps | **17.02 ps** | +1.66 |
| CO[1] → CO[3] | 24.91 ps | **26.72 ps** | −1.81 |
| CO[3] → CO[2] | 6.23 ps | **6.54 ps** | −0.31 |
| CO[2] → CO[0] | 17.30 ps | **16.97 ps** | +0.33 |

histogram 쪽이 표본이 4자릿수 많아 더 정확하고, **thermometer는 그 값을 어느 물리 소자에 붙일지를 확정해 준다.**

#### 이것이 바꾸는 것

**§2-6의 "판정 기준 실패"는 기준 자체가 틀린 것이었다.** "CARRY4 간 배선을 건너는 구간이 가장 넓어야 한다"고 했는데, 배선 구간은 `%4==0` = **17.02 ps로 2위**이고 최대는 `%4==1`(CO[1]→CO[3], 26.72 ps)인 **내부 구간**이다. Won 2016의 "every fourth bin에 배선 지연이 더해진다"는 이 소자·이 배치에서는 성립하지 않는다.

그리고 **§4에서 `%4` 접근을 접은 주된 이유(bin이 어느 물리 소자인지 모름)가 해소됐다.**

## 3. C2 — 배율 하나로 온도 보정이 되는가

### 3-1. 무엇을 계산했나

**주장의 배경:** Pan 2014(*IEEE TNS* 61(3))은 이렇게 주장했다.

> "We can assume that the whole delay chain expands or shrinks with variation of temperature but **each bin contributes the same ratio to the whole delay chain**."
> 잔차: **"maximum time offset of 3.5 ps (at bin 102)"**

**이 주장이 참이면 온도 보정이 공짜다.** 모든 탭이 똑같이 1 % 좁아졌다면 누적값인 LUT도 전부 1 % 줄어드니, LUT를 다시 만들 필요 없이 **전체에 0.99를 곱하면 끝**이다.

**그래서 우리 칩에서 그게 되는지 확인했다.**

**무슨 데이터로:** `python/histo_temp/histo_40_{1,2,3}.csv`(기준)와 `histo_80_{2,3}.csv`(대상), 6쌍.

**어떻게:**
1. 각 캡처의 히스토그램으로 LUT를 만든다 (§0-2 식)
2. 40 °C LUT에 배율 `k` 하나를 곱해 80 °C LUT를 예측한다
3. 예측 − 실측 = 잔차. 270개가 나온다
4. 최대 잔차와 가중 RMS를 낸다 (§0-4)

**`k`는 누가 어떻게 구했나 — 중요:**
`k`는 **파이썬 분석에서만 계산했고 하드웨어·COE에 적용한 적 없다.** 40 °C와 80 °C LUT를 **둘 다 손에 쥔 상태에서** 오차가 최소가 되도록 최소자승으로 역산했다(예: `k = 0.9905`).

**이 값은 현실에서 구할 수 없다.** 80 °C LUT를 이미 알아야 나오는데, 그걸 알면 배율 보정이 애초에 필요 없다. Pan의 실제 방식은 별도 기준 채널로 온도계수를 추정하는 것이라 반드시 오차를 안는다.

**즉 Pan 방식에 반칙을 허용한 조건이다.** 그런데도 잔차가 남으면, 실제 구현은 반드시 이보다 나쁘다.

### 3-2. 배율이 애초에 일정하지 않다

잔차를 계산하기 전에 이미 답이 보인다. 탭별로 폭이 어떻게 변했는지 보면 (`histo_40_1` → `histo_80_2`, 넓은 탭만 발췌):

| 탭 | 40 °C 폭 | 80 °C 폭 | 배율 | 절대 변화 |
|---|---|---|---|---|
| 1 | 76.68 ps | 74.89 ps | 0.977 | −1.79 ps |
| 37 | 53.02 | 50.23 | **0.947** | −2.79 ps |
| 50 | 16.10 | 18.33 | **1.139** | +2.23 ps |
| 150 | 22.84 | 25.56 | **1.119** | +2.72 ps |
| 270 | 33.00 | 33.21 | 1.006 | +0.21 ps |

**앞쪽 탭은 줄고 중간 탭은 늘었다.** 배율이 전부 같아야 "배율 하나로 보정 가능"인데 0.947 ~ 1.139다. **0.99를 곱해 탭 1을 맞추면 탭 50이 더 틀어진다.**

전체 폭 합은 양쪽 다 5000 ps로 같다. **늘거나 준 것이 아니라 탭들끼리 재분배된 것이다.**

> ⚠️ **좁은 탭의 비율은 쓰지 않았다.** 탭 185는 1.04 → 5.91 ps로 비율 5.7배지만 절대 변화는 4.87 ps뿐이다. 폭이 1~2 ps인 탭의 비율은 의미가 없다. 7/29 리포트가 이 함정에 빠졌다(§4).

| **신호 / 잡음** | **10 배** | |
| **Pan 2014 대비** | **12 배** (3.5 ps) | |

**거리로 환산하면** (빛 0.3 mm/ps, ToF는 왕복이므로 ÷2): 최대 6.4 mm, 평균 3.3 mm. 온도가 40 °C 오르면 거리가 그만큼 틀린다.

**결론: 배율 보정으로는 부족하다. LUT를 통째로 다시 만들어야 한다.**

### 3-4. ★ 정정 — 이전 66.7 ps는 경계 탭이 만든 값이었다

초판에 보고한 66.7 ps는 계산 구간을 `1~281`로 잡은 값이다. **최대 잔차가 나온 위치가 tap 281, 즉 구간의 맨 끝이었다.**

```
tap 281 :  40 °C 폭 1.27 ps  ->  80 °C 폭 42.06 ps   (33배)
```

**탭이 넓어진 것이 아니다.** 40 °C에서는 캐리가 그 탭에 겨우 닿아 반쯤만 존재했고, 80 °C에서는 체인이 빨라져 여유 있게 닿은 것이다. **체인 길이와 클럭 주기의 경계 효과이지 형상 변화가 아니다.**

구간 상한을 바꿔가며 확인하면:

| 계산 구간 | 최대 잔차 | 가중 RMS | 최대 위치 |
|---|---|---|---|
| 1~**281** | **67.25 ps** | 23.30 ps | 281 ← 경계 |
| 1~278 | 43.26 | 22.72 | 278 |
| 1~275 | 41.39 | 22.66 | 275 |
| 1~270 | 43.39 | 22.56 | 270 |
| 1~265 | 43.82 | 22.37 | 263 |
| 1~260 | 44.79 | 22.04 | 258 |
| 1~250 | 47.90 | 21.29 | 250 |

**281만 튀고 나머지는 41~48 ps로 안정적이다.** 가중 RMS는 21~23 ps로 구간에 거의 무관하다.

**→ 헤드라인 수치를 42.7 ps로 정정한다.** 결론(배율 보정 불가)은 바뀌지 않는다 — 여전히 잡음의 10배, Pan의 12배다.

### 3-5. ★★ CO 빌드의 온도 특성 — 논문 전제가 무너졌다

**무슨 데이터로:** `python/co_temp/co_histo_{40,50,60,70,80}_{1..4}.csv` (CO 빌드, 40~70 °C 3회 · 80 °C 4회). 열평형 프로토콜 개선(반복 간 다이 온도 드리프트 0.25~0.62 °C, O 시리즈는 0.74~1.23 °C였음).

**결과 — 온도별 무보정 드리프트:**

| ΔT (다이) | O 빌드 | **CO 빌드** |
|---|---|---|
| +12 °C | 26.7 ps | **5.7 ps** |
| +19 °C | 36.8 ps | **12.9 ps** |
| +29 °C | 39.2 ps | **13.3 ps** |
| **+40 °C** | **69.7 ps** | **8.3 ps** |

**CO 빌드는 40 °C가 올라가도 아무 보정 없이 8.3 ps밖에 안 틀린다.**

**40 → 80 °C 정리 (구간 2~272, 경계 제외, 12쌍):**

| | 최대 오차 | 가중 RMS | 거리(왕복) |
|---|---|---|---|
| **보정 안 함** | 9.0 ps | **3.7 ps** | 0.55 mm |
| 배율 보정 | 5.9 ps | 2.4 ps | 0.36 mm |
| 전체 재교정 | 1.0 ps | 0.4 ps | 0.06 mm |
| **양자화 잡음** (LSB 18.45/√12) | — | **5.3 ps** | 0.80 mm |

#### 이것이 뜻하는 것

**온도 오차(3.7 ps)가 TDC 자체의 양자화 잡음(5.3 ps)보다 작다.** 보정을 완전히 포기해도

$$\sqrt{3.7^2+5.3^2}=6.48\ \text{ps} \quad \text{vs} \quad \text{완전보정 } 5.33\ \text{ps}$$

즉 **단발 측정에서는 온도 보정이 사실상 무의미하다.**

> ⚠️ **단, 평균화하면 얘기가 달라진다.** 양자화 잡음은 평균 횟수 N에 대해 1/√N로 줄지만 **온도 오차는 계통 오차라 줄지 않는다.**
> ```
> N=1   : 양자화 5.3 ps  >  온도 3.7 ps   -> 보정 불필요
> N=10  : 양자화 1.7 ps  <  온도 3.7 ps   -> 온도가 지배
> N=100 : 양자화 0.5 ps  <  온도 3.7 ps   -> 온도가 완전히 지배
> ```
> FMCW처럼 수천 번 평균하는 응용에서는 3.7 ps가 그대로 바닥으로 남는다. 그때는 배율 보정으로 2.4 ps, 전체 재교정으로 0.4 ps까지 갈 수 있다.

#### 논문에 미치는 영향

**§3-3의 42.7 ps는 온도 특성이 아니라 잘못된 탭 선택의 결과였다.** 이중 체인 무정지 재교정 구조는 "배율로는 부족하니 전체 재교정이 필요하다"를 전제로 하는데, CO 빌드에서는 **재교정이 필요한지조차 응용에 따라 달라진다.** 전제가 성립하지 않는다.

**대신 새로운 주장이 나온다:**

> 어느 CARRY4 출력을 탭으로 쓰느냐가 딜레이라인의 온도 안정성을 결정한다. XOR 출력(O/S)은 40 °C 변화에 69.7 ps 드리프트하고, 캐리 출력(CO/C)은 8.3 ps에 그친다. 올바른 선택이면 한 온도에서 만든 LUT가 전 구간에서 유효하다.

Carra *TNS* 2018은 C/S 16조합을 비교했으나 **상온 정적 DNL만** 봤다. 온도 안정성 비교는 로컬 27편에 없다(§5-2).

**그림:** `fig/2026-08-04_co_vs_o_temperature.png`

![CO vs O 온도 특성](fig/2026-08-04_co_vs_o_temperature.png)

그림 (a)를 보면 **탭별 변화량 자체는 두 빌드가 거의 같다**(|Δ| 평균 1.68 vs 1.47 ps). 그런데 (c)의 누적을 보면 갈린다 — **O는 앞쪽 절반이 좁아지고 뒤쪽이 넓어지는 장거리 쏠림이 있어 누적이 −70 ps까지 벌어지고, CO는 변화가 국소적으로 상쇄되어 ±8 ps에 머문다.** LUT는 폭의 누적이므로 중요한 것은 변화의 크기가 아니라 **쌓이느냐 상쇄되느냐**다.

(b)의 상대 변화는 두 빌드 구분이 안 된다 — 폭 1~2 ps 탭에서 절대 변화 0.1 ps가 수십 %로 나타나기 때문이다. 판단은 (a)의 절대값과 (c)의 누적으로 해야 한다.

#### ⚠️ 아직 통제되지 않은 것

O 온도 시리즈는 **7/29 빌드** 데이터다. §2-7에서 재합성만으로 INL이 15 % 움직이는 것이 확인됐으므로, **`o_rebuild` 빌드로 40/80 °C를 다시 재야** 69.7 ps vs 8.3 ps를 탭 소스 탓이라 확정할 수 있다(§8-1).

### 3-6. ★★ 물리 소자별 온도계수 — CARRY4 내부에서 무엇이 움직이는가

§2-8에서 bin↔물리 소자 대응이 확정됐으므로, 온도 데이터를 **물리 소자 단위로** 다시 볼 수 있다. 지금까지 "`%4` 그룹"이라고만 부르던 것에 이름이 붙는다.

**무슨 데이터로:** `python/co_temp/co_histo_*.csv` (CO 빌드, 40~70 °C 3회 · 80 °C 4회), 탭 2~272.
**어떻게:** 각 캡처에서 `w[i] = h[i]/H × 5000` 후 `%4` 그룹의 **평균 폭**을 낸다(비율의 평균이 아니라 **평균의 비율** — §4-1의 지표 B). 다이 온도에 대해 회귀.

| 물리 구간 | 40 °C | 80 °C | 변화 | ps/°C | **ppm/°C** |
|---|---|---|---|---|---|
| CO[1] → CO[3] | 32.13 ps | 31.53 ps | −1.9 % | −0.0147 | **−458** |
| **CO[2] → CO[0]** | 19.56 ps | 21.82 ps | **+11.6 %** | +0.0547 | **+2795** |
| CO[0] → 다음단 CO[1] (배선) | 17.15 ps | 16.38 ps | −4.5 % | −0.0184 | **−1076** |
| **CO[3] → CO[2]** | 5.17 ps | 4.26 ps | **−17.6 %** | −0.0217 | **−4202** |
| 합계 (CARRY4 단당) | 74.00 ps | 73.99 ps | −0.0 % | −0.0002 | −3 |

**합계가 0인 것은 정규화 때문이다(스케일 소거). 의미 있는 것은 구간 간 재분배다.**

#### 이 결과는 견고하다 — 이전 `%4` 분석과 무엇이 다른가

§4에서 `%4` 접근을 접은 이유는 두 가지였다. 둘 다 해소됐다.

| 이전 문제 | 현재 |
|---|---|
| bin이 어느 물리 소자인지 모름 | ✅ §2-8에서 확정 |
| 지표 A(비율의 평균)가 좁은 탭에 지배됨 | ✅ 지표 B(평균의 비율)만 사용 |
| 그룹내 편차 > 그룹간 편차 (비 1.56) | ⚠️ 그건 **폭**의 산포. 여기서 재는 것은 **그룹 평균의 온도 변화**이고, 그 평균의 반복 재현성은 아래처럼 매우 높다 |

**유의성 — 반복 산포 대비:**

| 물리 구간 | 40 °C 3회 산포 | 80 °C 4회 산포 | 변화량 | 배수 |
|---|---|---|---|---|
| CO[1] → CO[3] | ±0.016 ps | ±0.050 ps | 0.60 ps | **9×** |
| CO[2] → CO[0] | ±0.014 ps | ±0.094 ps | 2.26 ps | **21×** |
| CO[0] → 다음단 CO[1] | ±0.013 ps | ±0.101 ps | 0.76 ps | **7×** |
| CO[3] → CO[2] | ±0.018 ps | ±0.029 ps | 0.91 ps | **19×** |

**단조성 — 5개 온도점 전부:**

| 물리 구간 | 40 °C | 50 °C | 60 °C | 70 °C | 80 °C | |
|---|---|---|---|---|---|---|
| CO[1] → CO[3] | 32.130 | 31.983 | 31.910 | 31.717 | 31.531 | ✅ |
| CO[2] → CO[0] | 19.555 | 20.162 | 20.613 | 21.121 | 21.819 | ✅ |
| CO[0] → 다음단 CO[1] | 17.147 | 16.953 | 16.787 | 16.635 | 16.381 | ✅ |
| CO[3] → CO[2] | 5.170 | 4.902 | 4.689 | 4.523 | 4.262 | ✅ |

**네 구간 전부 5개 온도점에서 단조**다. 잡음이라면 나올 수 없는 패턴이다.

#### 의미

**CARRY4 내부의 네 구간이 서로 다른 온도계수를 갖는다** — `−4202` ~ `+2795` ppm/°C로 **약 7000 ppm/°C 벌어진다.** 반면 단당 합계는 `−3 ppm/°C`로 사실상 0이다.

> **딜레이라인은 온도에 따라 전체가 늘거나 주는 것이 아니라, CARRY4 내부에서 시간이 재분배된다.**

이것이 §3-3에서 "배율 하나로는 안 된다"의 물리적 정체다. 다만 CO 빌드에서는 그 재분배가 **누적되지 않고 국소적으로 상쇄**되어(§3-5 그림 c) 최종 LUT 오차가 8.3 ps에 그친다.

> ⚠️ **메커니즘은 여전히 미해결.** 어느 소자가 왜 그런 온도계수를 갖는지는 설명하지 못한다. `CO[3] → CO[2]`가 −4202 ppm/°C로 가장 민감한데, 이 구간은 look-ahead 경로 두 개의 차이라 단순한 소자 하나에 대응되지 않는다.

**변환:** `T[°C] = (raw >> 4) × 503.975/4096 − 273.15` (XADC 온도 레지스터 규격).

| 설정 | #1 | #2 | #3 | #3 − #1 |
|---|---|---|---|---|
| 40 °C | 41.96 | 42.20 | 42.70 | **+0.74** |

**5개 설정점 전부 상승, 평균 +0.98 °C.** 열평형에 도달하기 전에 측정했다.

**의미:** 히스토그램은 약 60초간 누적되는데 그 사이 온도가 1 °C 움직였다. **각 캡처는 단일 온도가 아니라 1 °C 구간의 스미어다.** 40 °C 반복 산포가 큰 것(#1↔#3이 최악)도 이것으로 설명된다.

## 4. `tap%4` 분석 철회

### 4-1. 7/29 리포트 수치의 문제 — 지표 선택

7/29 리포트 §2-2 표를 **자릿수까지 정확히 재현**했다. 계산 오류가 아니다. 문제는 어떤 통계량을 썼느냐다.

`shape[i] = h[i] / mean(h)` (정규화로 스케일 소거) 위에서:

| 지표 | 정의 | 문제 |
|---|---|---|
| **A** (7/29) | 탭별 상대변화 `(s₈₀−s₄₀)/s₄₀`를 구한 뒤 그룹 내 **산술평균** | 폭과 무관하게 1표씩 |
| **B** | 그룹 **평균 폭의 변화율** | 폭에 비례해 반영 |

같은 데이터(탭 1~273), 지표만 바꾼 결과:

| 40→80 °C | `%4==0` | `%4==1` | `%4==2` | `%4==3` |
|---|---|---|---|---|
| A | +10.5 | +11.9 | +11.1 | −12.1 |
| **B** | **−1.8** | **+3.6** | **+1.3** | **−14.0** |

**왜 갈리나** — 폭 사분위로 나누면:

| 폭 구간 | 탭 수 | 평균 폭 | A | B |
|---|---|---|---|---|
| 가장 좁은 25 % | 68 | **2.43 ps** | **+27.2 %** | +2.1 % |
| 중간 50 % | 136 | 16.13 ps | −3.0 % | −0.6 % |
| 가장 넓은 25 % | 69 | 38.28 ps | +0.4 % | +0.4 % |
| **전체** | 273 | 18.32 ps | **+5.4 %** | **−0.0 %** |

정규화 때문에 전체 변화는 **정의상 0이어야 하는데 A는 +5.4 %를 낸다.**

**결정적 증거 — A는 구간을 바꾸면 무너진다:**

| 구간 | `%4==1` |
|---|---|
| A, 1~273 | +11.9 |
| A, 1~281 | **+58.2** |
| B, 1~273 | +3.6 |
| B, 1~281 | +4.3 |

탭 8개를 더 넣었을 뿐인데 A가 5배로 튄다. **→ 7/29의 "+10.9 / +12.1 / +11.2 / −12.3"와 "형상 차이 11.9 %"는 폐기.**

### 4-2. 물리 해석 철회

`%4` 그룹에 물리 경로 이름을 붙였다가 두 번 뒤집고 전부 철회했다.

| 주장 | 철회 사유 |
|---|---|
| `%4==3`이 CARRY4 간 배선 구간 | RTL 미확인 상태의 추정. 매핑이 반대였음 |
| `%4==0`이 배선 구간이라 다르게 변한다 | 그 구간이 O 빌드 실측 최소폭(6.97 ps)이라 설명 불가 |
| O→FF 샘플링 경로 차이가 지배 | **Vivado 리포트로 반증.** FF가 CARRY4와 같은 슬라이스(`SLICE_X42Y16`)에 있고 O→D 배선 지연 0.000 ns, 클럭도 동일 |
| 온도가 O[1]/O[3] 순서를 뒤집는다 | fast/slow 코너는 P·V·T 묶음이라 T를 분리할 수 없음 |

### 4-3. ★ `%4` 프레임 자체가 약하다

| | O 빌드 | CO 빌드 |
|---|---|---|
| 그룹내 표준편차 / 그룹간 표준편차 | 1.38 | **1.56** |

**같은 `%4` 위치인데도 단마다의 편차가 그룹 간 차이보다 크다.** CO 빌드 `%4==0`은 stage 1에서 39.96 ps, stage 2에서 1.69 ps, stage 3에서 7.72 ps다(전체 범위 0.98 ~ 84.65 ps). CO 빌드에서 `%4==0`과 `%4==3`은 전체 평균과 통계적으로 구분되지도 않는다(t = +0.1, +0.2).

**→ 7/29의 형상 분석, §2-6의 판정 기준이 모두 분산의 절반도 설명하지 못하는 효과 위에 있었다.**

> ✅ **2026-08-05 갱신 — 이 절의 판단은 부분적으로 뒤집혔다.**
> 위 비(1.38~1.56)는 **탭 폭의 산포**를 말한다. 그런데 §3-6에서 재는 것은 **그룹 평균의 온도 변화**이고,
> 그 평균의 반복 재현성은 ±0.013~0.101 ps로 매우 높아 변화량(0.60~2.26 ps)의 7~21분의 1에 불과하다.
> 또 접었던 주된 이유였던 **bin↔물리 소자 대응 불명이 §2-8에서 해소**됐다.
> **따라서 지표 B(평균의 비율)로, 확정된 대응표를 써서 하는 `%4` 분석은 유효하다.** 폐기 대상은
> ① 지표 A 기반 수치(§4-1) ② 근거 없는 물리 해석(§4-2) ③ 개별 탭 단위 주장 — 이 셋이다.

## 5. 논문 신규성 검토

`paper/ref/` 27편을 `pypdf`로 전문 추출 후 키워드 전수 스캔 + 핵심 논문 정독.

### 5-1. CO/O 비교는 이미 발표됨

**Carra et al., *IEEE TNS* 65(2), Feb 2018, "Design and Characterization of a Low-Cost FPGA-Based TDC"** 원문:

> "Each CARRY4 primitive has four delay elements, each providing two distinct outputs: the **carry output, from the multiplexer gate (C)**, and the **sum output, from the XOR gate (S)**. … The designer is free to select which output to consider."
> "**We tested all 16 combinations of C and S patterns for our FPGA, and discovered that the best output pattern is given by the classical CCCC.**"

- C/S 선택 **16조합 전수 비교가 2018년에 발표**됨
- 최적이 **CCCC(= 오늘 바꾼 것)**이고 저자들이 이를 **"the classical"**이라 부름
- 참고문헌 [17]은 Spartan-6에서 SCSS가 최적이라 보고

**우리가 한 것은 비표준에서 표준으로 돌아온 것이다. 논문 기여가 될 수 없다.**

덤: 그들은 **NCCC 다운샘플링**(CARRY4당 1탭 무시)으로 σ를 0.65 → 0.42(−35.4 %)까지 더 낮췄다. 우리 개선폭(0.807 → 0.664, −17.8 %)보다 크다. 기존 기법이지만 **popcount에서 탭 하나만 빼면 되니 시도해볼 가치는 있다.**

### 5-2. 살릴 수 있는 각도 — 온도 안정성

Carra 2018은 **상온 정적 DNL만** 비교했다. **C 패턴과 S 패턴의 온도 드리프트를 비교한 논문은 로컬 27편에 없다.**

물리적 근거도 있다 — O 탭은 경로에 **XOR 게이트(능동 로직)**가 들어가고 CO 탭은 **순수 MUXCY 캐리 경로**다. 능동 로직이 빠지면 온도 민감도가 줄어드는 것이 자연스럽다.

**검증 방법:** O 빌드 온도 데이터는 이미 있다(`histo_temp`). CO 빌드 온도 시리즈를 찍어 C2를 비교하면 된다.

```
O  빌드 : 배율보정 잔차 42.7 ps  (측정 완료)
CO 빌드 : ?                      (내일)
```

CO 쪽이 유의하게 낮으면 **"탭 소스 선택은 정적 선형성뿐 아니라 온도 안정성도 바꾼다"**가 되고, 이는 자가교정 주제와 직결된다 — **드리프트가 작을수록 재교정 주기가 길어지고 아키텍처가 싸진다.**

### 5-3. 남은 빈칸 — 이중 체인 자가교정

Pan 2014 서론이 문제를 문장으로 정의해 놓았다:

> "If the signals to be measured are **statistically random** …, the LUT can be updated by **swapping ping-pong memories without introducing any dead time**; **otherwise, a dedicated calibration signal is required, and dead time will be introduced**."

- **"ping-pong"은 이미 점유된 용어**(LUT 메모리 더블버퍼링). 아키텍처 이름으로 쓰면 안 됨
- 문제의식 자체는 2014년부터 알려짐

| | 전체 형상 갱신 | dead time 0 | 측정신호 통계 무관 |
|---|:--:|:--:|:--:|
| Wu (ping-pong memory) | ✅ | ✅ | ❌ |
| Won *TBCAS* 2016 (on-the-fly FIFO) | ✅ | ✅ | ❌ |
| Pan 2014 (전용 체인) | ❌ 스칼라만 | ✅ | ✅ |
| **역할교대 이중 체인** | ✅ | ✅ | ✅ |

세 칸을 동시에 채운 사례가 로컬 27편에 없다.

**주요 리스크:** ① 리소스 2배 ② **두 체인 간 스큐** — 오프셋 자체가 온도 의존적이라 교대 시 계단 발생. 정량화 필수 ③ 명명(ping-pong 금지)

### 5-4. 접근 권한 한계

로컬 PDF 27편은 전문 접근 가능하나 **IEEE Xplore 유료 전문은 구독 없음.** 2020~2026 최신 논문에 동일 구조가 있는지 확증하지 못했다. 투고 전 `dual-stimulus calibration`, `redundant delay line calibration`, `role rotation TDC` 웹 재조사 필요(로드맵 T15).

### 5-5. 아키텍처 A 폐기

FMCW를 이번 논문에서 배제하기로 했으므로 "광학 플라이백 데드존 활용" 구조는 전제가 사라진다. OPLL 논문으로 이월.
