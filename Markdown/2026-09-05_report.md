어제 : Vivado 켜기 → ILA 무장 → 사람이 BTNU 누르기 → CSV 받기

## 1. 무엇을 만들었나 — 다섯 덩어리

### 1-1. 히스토그램을 AXI로 읽게 했다 (커밋 `0a66572`)

**전에는** 히스토그램(탭마다 몇 발 왔는지를 담은 384칸 표)을 칩 밖으로 빼는 길이
ILA밖에 없었다. ILA는 Vivado가 있어야 쓸 수 있다.

**이제는** PS가 주소 `0x43C0_1000 + 탭번호×4`를 읽으면 그 탭의 카운트가 나온다.
메모리를 읽는 것과 똑같다.

> **어떻게 했나** — 히스토그램 메모리(BRAM)는 문이 두 개 달린 방이다. 한쪽 문으로는
> TDC가 계속 값을 쌓고, 다른 쪽 문으로는 읽는다. 원래 두 문이 같은 시계(200 MHz)를
> 쓰고 있었는데, **읽는 쪽 문만 AXI 시계(100 MHz)로 바꿨다.** 7-series BRAM은 원래
> 문마다 시계가 달라도 되게 만들어진 물건이라 이게 된다. 그 덕에 두 시계 사이를
> 건너는 복잡한 처리가 **아예 필요 없어졌다.**

**함정 하나** — BRAM은 주소를 걸고 나서 값이 나오기까지 시간이 걸린다. 바로 읽으면
**직전 주소의 값**이 나온다. ILA 시절에도 똑같은 함정에 빠져 주소를 한 클럭 늦추는
방식(`probe_read_addr_d1`)으로 해결했었다. 이번에도 같은 처리를 넣었다.

### 1-2. ILA를 아예 뺐다 (같은 커밋)

ILA로만 볼 수 있던 값이 남지 않게 되자 IP 자체를 제거했다. 효과가 컸다:

| | 있을 때 | 뺀 뒤 |
|---|---|---|
| 타이밍 여유 (WNS) | +0.089 ns | **+0.209 ns** |
| BRAM 사용 | 42 / 140 | **1 / 140** |

**BRAM 42개 중 41개가 ILA 것이었다.** 어제 "타이밍 임계경로가 ILA IP 안에 있다"고
본 것이 수치로 확인됐다.

### 1-3. 측정 절차를 하드웨어가 밟게 했다 — 시퀀서 FSM (커밋 `0ff8a24`)

사용자가 지정한 6단계를 그대로 구현했다:

```
S_IDLE → S_RO_ENABLE → S_MEAS_FREQ → S_STABILIZE → S_HISTOGRAM → S_DONE
 대기    링오실레이터   주파수 측정    히스토그램     누적          완료
         켜고 안정화    (10 ms 게이트)  지우기
```

`CTRL.START`를 한 번 쓰면 이 순서가 저절로 돈다.

**★ 링오실레이터가 오늘 처음으로 꺼졌다.** 종전 RTL은 `ro_enable_reg <= clk_locked`
한 줄이라, 전원을 넣고 클럭이 잠기는 순간부터 **영영 발진했다.** 끄는 조건이 아예
없었다. 이제 FSM이 켜고 끈다.

### 1-4. Mode 2(외부 신호 실측) 회로 (커밋 `5c77443`)

히트 하나하나의 시각을 순서대로 쌓는 **캡처 버퍼**를 만들었다. 4096발 × 64비트.

> 히스토그램이 "탭마다 몇 발"이라면, 캡처 버퍼는 "몇 시 몇 분에 왔는가"를 하나씩
> 적어두는 장부다. 코드밀도 교정에는 앞의 것이, 실제 거리 측정에는 뒤의 것이 필요하다.

64비트인 이유: 하드웨어가 계산한 타임스탬프가 48비트라 32비트 한 칸에 안 들어간다.

**히트 소스를 실행 중에 고를 수 있게 했다.** Mode 1(링오실레이터)과 Mode 2(외부 신호)는
샘플링 클럭이 같아서, 신호선만 골라주면 된다. **비트스트림 하나로 두 모드를 쓴다.**

### 1-5. 그 대가 — 그리고 그 때문에 고친 것 (같은 커밋)

히트 소스를 고르는 판단 로직이 들어가면서 **LUT(작은 논리 회로) 하나**가 히트 경로에
끼었다. 그것 하나가 **약 370 ps**를 더했다. 자세한 내용은 §3에서 다룬다.

## 2. 실물 검증 — 세 번 다 통과

전부 XSCT(JTAG로 ARM 코어를 조종하는 도구)로 보드에서 직접 확인했다.
**Vitis에서 손으로 할 일을 스크립트에 미리 적어둔 것**이고, C 프로그램을 보드에 올릴
필요가 없다.

| 단계 | 스크립트 | 결과 |
|---|---|---|
| 1단계 (레지스터) | `tcl/xsct_stage1_check.tcl` | 4/4 통과 |
| 2단계 (히스토그램 리드백) | `tcl/xsct_stage2_check.tcl` | 5/5 통과 |
| 3단계 (시퀀서 FSM) | `tcl/xsct_stage3_check.tcl` | 6/6 통과 |
| Mode 2 회로 + 회귀 | `tcl/xsct_mode2_check.tcl 0` | 통과 (Mode 2 자체는 미검증) |

### ★ 가장 중요한 확인 : `HIT_CNT == 384탭 합`

```
목표 200만 발 →  HIT_CNT 2,000,000  ==  384칸 합 2,000,000   차이 0
```

**왜 이게 중요한가.** 탭 폭을 `w[i] = h[i]/H × 5000 ps`로 정의한다(`H`는 총 히트 수).
`H`가 틀리면 **모든 탭 폭이 그 비율만큼 통째로 틀어지고, 폭의 합이 5000 ps가 아니게
된다.** 이제 `H`를 하드웨어가 보고한 값으로 믿을 수 있다.

> **함정이 하나 있었다.** 히스토그램은 히트 하나를 넣는 데 4클럭이 걸리고, 그 사이에
> 온 히트는 버려진다(데드타임 20 ns). 그래서 "도착한 히트"를 세면 실제로 들어간 것보다
> 많아진다. **히스토그램이 "받아들였다"고 알린 것만** 세도록 만들었다.

### 데드타임 손실 실측 : 0.00 % — 내 사전 추정 2.4 %는 틀렸다

200만 발 중 한 발도 안 버려졌다. 추정이 틀린 이유는 히트를 **무작위 도착으로
가정**했기 때문이다. 실제 링오실레이터 히트는 64분주로 만든 **거의 일정한 간격**의
신호라(951 ns = 190클럭), 데드타임 4클럭과 겹칠 일이 사실상 없다.

**그래도 이 카운터는 필요하다.** Mode 2에서는 신호가 진짜 무작위로 오므로 손실이
생긴다. 그때 이 값이 실제 정보가 된다.

## 3. ★ 오늘의 가장 중요한 발견 — 측정 창이 미끄러진다

### 3-1. 무슨 일이 있었나

히트 소스를 고르는 LUT이 들어간 뒤 Mode 1을 다시 재보니, 히트가 찍히는 탭 범위가
**2~321에서 24~348로 옮겨갔다.**

처음에는 "망가졌다"고 판단했으나, 제대로 분석해보니 **아니었다.**

| 구간 (폭 합, ps) | 먹스 없음 | 먹스 있음 |
|---|---|---|
| 탭 0~23 | **364.5** | **0.0** |
| 탭 24~99 | 1194.7 | 1167.5 |
| 탭 100~299 | 3069.2 | 3079.0 |
| 탭 300~321 | 371.6 | 373.9 |
| 탭 322~349 | **0.0** | **379.5** |
| 전체 | 5000.0 | 5000.0 |

**아래에서 사라진 364.5 ps가 위에 379.5 ps로 나타났고, 가운데는 그대로다.**

지연선 자체는 안 변했다 — `tap%4` 평균 폭(12.74/26.03/3.74/19.99 → 12.05/25.81/3.97/19.44 ps)도,
양자화 한계 σ(7.59 → 7.07 ps)도 거의 같다.

### 3-2. 왜 이런 일이 생기나 — 쉽게

TDC는 "히트가 온 뒤 다음 클럭 에지까지 몇 칸을 갔나"를 센다.

**히트가 370 ps 늦게 도착하면 갈 시간이 그만큼 줄어드니 칸 수가 작아진다.** 원래 0~23칸
쯤 가던 히트들은 이제 음수가 되는데, 그럴 수는 없으므로 **다음 클럭 에지로 넘어가면서
반대로 아주 큰 칸 수(322~349)로 감긴다.** 사라진 364.5 ps와 나타난 379.5 ps가 그 양이다.

즉 자(尺)가 망가진 게 아니라 **자를 대는 위치가 옮겨간 것**이다.

### 3-3. 뜻밖의 이득과 대가

**이득** : 캐리체인 진입부의 이상 구간이 측정 창 밖으로 나갔다. 탭 3의 폭이 44.98 ps로
평균(15.6 ps)의 3배였는데(오래된 알려진 문제), 이제 그 탭을 아예 안 쓴다.

**대가** : 체인 끝까지 여유가 63탭 → 35탭으로 줄었다. 온도가 오르면 체인이 느려져
더 많은 탭이 필요한데, 그만큼 여유가 깎였다.

### 3-4. 그리고 창은 재빌드마다 흔들린다

같은 RTL인데 다시 빌드하니 창 끝이 349 → 348로 1탭 달라졌다.

| 빌드 | 히트 경로 | 창 |
|---|---|---|
| 09-04 `zed_mode1` | 로직 없음 | 2 ~ 322 |
| 09-05 `zed_axi2` | 로직 없음 | 2 ~ 321 |
| 09-05 `zed_fsm` | 로직 없음 | 2 ~ 321 |
| 09-05 `zed_mode2` (1차) | LUT4 | 24 ~ 349 |
| 09-05 `zed_mode2` (재빌드) | LUT4 | 24 ~ 348 |

전에는 히트 경로에 로직이 하나도 없고 양 끝이 XDC로 위치 고정이라 배선이 거의
결정돼 있었다. 이제 **Vivado가 위치를 정하는 LUT**이 끼었으니 빌드마다 달라진다.

## 4. 그래서 고친 것 — `danger_zone`을 소프트웨어가 정하게

### 4-1. `danger_zone`이 무엇인가

TDC는 시간을 두 부분으로 잰다 — **시침**(coarse, 클럭을 몇 번 셌나)과
**분침**(fine, 그 5 ns 안에서 어디쯤인가).

3시 정각에 시침을 읽으면 2시로도 3시로도 읽힌다. **한 시간(=5 ns)이 통째로 틀린다.**
그래서 **반 주기 어긋난 보조 시계**를 두고, 분침이 위험 구간에 있으면 그쪽을 읽는다.

```verilog
if (fine < 40 || fine > 220)  →  보조 시계를 읽어라
else                          →  본 시계를 읽어라
```

### 4-2. 창이 밀리자 이 경계가 안 맞게 됐다

| | 종전 상수 (40/220) | 자동 설정 (66/304) |
|---|---|---|
| 아래 가드 | **228 ps** | **642.6 ps** |
| 위 가드 | 1980 ps | 636.0 ps |

상수일 때는 **9배 비대칭**이었다. 아래쪽 안전 여유가 얇아졌고, 위쪽은 에지와 무관한
탭 221~300까지 불필요하게 위험으로 분류하고 있었다.

40/220은 원래 창이 0~320이던 시절 값이고, 코드 주석에도 **"옛 O탭 분포로 튜닝된
것이라 재튜닝이 필요한데 아직 안 했다"** 고 적혀 있던 값이다. 즉 먹스가 문제를 만든 게
아니라, **원래 근거가 없던 값의 문제를 드러낸 것**이다.

### 4-3. 세 가지를 넣었다

1. **`DANGER_LO/HI`를 상수 → AXI 레지스터** (`0x44`). 재빌드 없이 바꿀 수 있다.
2. **소프트웨어가 히스토그램에서 창을 읽어 스스로 정한다.** 양 끝에서 630 ps씩 세어
   들어간 지점을 경계로 삼는다.
3. **여유 검사**를 검증 스크립트에 추가. 체인 끝까지 20탭 미만이면 실패로 잡는다.

> **630 ps의 근거**는 먹스 없던 빌드에서 상수 40이 만들던 아래 가드 폭이다.
> **"예전과 같은 여유를 창이 어디로 가든 유지한다"** 는 뜻이지 630 ps가 옳다는 뜻이
> 아니다. **시침이 실제로 흔들리는 시간은 이 프로젝트에서 한 번도 측정된 적이 없다.**
> 이제 레지스터라, 값을 좁혀가며 타임스탬프가 5000 ps 튀는 지점을 찾는 실험이 가능하다.

### 4-4. 내 판정 기준이 틀렸었다

처음에는 `창 시작 != 2 || 창 끝 != 321`로 검사해 **멀쩡한 것을 실패로 판정했다.**
창의 절대 위치는 히트 경로 지연에 따라 미끄러지는 값이지 지연선 품질이 아니다.
**진짜 기준은 체인 끝까지 남은 여유다.**

## 5. 문서 오류 하나를 잡았다 — 링오실레이터 주파수

`Data/20260904_zed_mode1/README.md`에 **"링오실레이터 111.0 MHz"** 라고 적혀 있었는데
**2배 틀린 값**이었다. 올바른 값은 **55.5 MHz**다.

환산식이 RTL에서 따라온다:

```
f_RO = RO_CNT × 4 / 게이트(10 ms)          히트율 = f_RO / 64
```

어느 쪽이 맞는지는 히트율로 갈린다. 세 측정 모두 55.5 MHz 쪽이 맞았다:

| 측정 | RO_CNT | f_RO | 예상 히트율 | 실측 히트율 |
|---|---|---|---|---|
| 09-04 | 138,716 | 55.49 MHz | 0.867 MHz | 0.867 MHz (그 문서의 값) |
| 09-05 2단계 | 196,072 | 78.43 MHz | 1.226 MHz | 1.229 MHz (614만발/5초) |
| 09-05 3단계 | 168,194 | 67.28 MHz | 1.051 MHz | 1.05 MHz (200만발/1.9초) |

**같은 문서 안에서 주파수와 히트율이 서로 모순이었다.** 환산식이 코드 어디에도 없어서
생긴 일이라, `tdc_axi_regs.v`의 `A_ROCNT` 주석에 식을 박아 두었다.

> RO 주파수가 빌드마다 다른 것(55.5 → 78.4 → 67.3 MHz)은 재배치로 링 경로가 달라진
> 결과로 **보인다** — 넷리스트 미확인 가설이다. 코드밀도 교정에는 링 주파수가 들어가지
> 않으므로(히트가 무작위이기만 하면 된다) 측정 결과에는 무관하다.

## 6. 부수 확인 — 클럭 소스를 바꿔도 지연선은 그대로 (커밋 `dd02425`)

어제 TDC 클럭의 뿌리를 보드의 Y9 발진기에서 **PS7의 FCLK_CLK0**로 바꿨는데, 지금까지의
모든 탭 폭 수치가 Y9 기준이었다. 그대로 써도 되는지 확인했다.

| | Y9 (09-04) | FCLK (09-05) |
|---|---|---|
| **유효탭 상한** | **321** | **321** |
| **LSB** | **15.625 ps** | **15.625 ps** |
| 상한 뒤 꼬리 | 1칸 | **0칸** |
| 양자화 한계 σ | 7.35 ps | 7.29 ps |

**써도 된다.** 표본을 2.8배 더 모으고도 꼬리가 오히려 깨끗해졌으니, FCLK 지터가 탭 폭
측정에 유의미한 영향을 주지 않는다.

> ⚠ **판정 기준 정정** : "누적 시간이 탭 N에서 5000 ps에 닿는가"는 기준이 될 수 없다.
> `w[i] = h[i]/H × 5000` 정의상 합은 **언제나** 5000이다. 항등식이지 측정 결과가 아니다.
> 물리량은 **"히트가 어디서 끊기는가"** = 유효탭 상한 쪽이다. 이걸 세션 중 두 번
> 잘못 말했다.

## 9. 아직 안 된 것

- **Mode 2는 미검증이다.** 회로는 들어갔고 빌드·타이밍은 통과했지만 **외부 신호를
  실제로 받아본 적이 없다.** 고속 LVDS 비교기가 회사에 있다.
- **Mode 0(DPS)은 FSM이 받지 않는다.** 샘플링 클럭이 달라(`clk_200_shifted`) 런타임
  전환에 클럭 재설계가 필요하다. 대안은 **"클럭 대신 히트를 흔드는"** 방식인데,
  위상 스텝 대 fine 값의 **기울기 부호가 뒤집힌다.** `python/validate_timestamp.py`도
  함께 고쳐야 하고, 부호 말고 다른 게 안 바뀐다는 보장은 실측으로 확인해야 한다.
- **시침(coarse)이 실제로 흔들리는 시간이 미측정이다.** 이제 `DANGER` 레지스터로
  실험할 수 있다.
- **ZedBoard 온도 계수 미측정** (−1.2 %/40 °C는 회사 Zybo에서 빌려온 가정값).
- **J18 점퍼 실물 미확인** — 다만 내일 PMOD를 쓰면 이 문제는 비켜 간다.

## 10. 내일 할 일

### 10-1. STM32를 PMOD에 물려 Mode 2 첫 신호 받기

고속 비교기가 없으므로 STM32를 신호원으로 쓴다.

**RTL은 이미 준비해뒀다.** 되돌리기 쉽게 파라미터 하나로 전환된다:

```bash
# PMOD 단선 입력으로 빌드
vivado -mode batch -source build_zedboard.tcl -tclargs 2 zed_pmod 1 1
#                                                     mode 이름  빌드 HIT_INPUT
# 비교기가 돌아오면 마지막 인자만 0 으로 (또는 생략)
vivado -mode batch -source build_zedboard.tcl -tclargs 2 zed_fmc 1 0
```

| `HIT_INPUT` | 입력 | 핀 | 버퍼 | 뱅크 전압 |
|---|---|---|---|---|
| 0 (기본) | FMC LVDS 차동 | E21 / D21 | `IBUFDS` + `DIFF_TERM` | J18 = 2.5V 필요 |
| **1** | **PMOD 단선** | **Y11** | 없음 (자동 `IBUF`) | **3.3V 고정 — J18 무관** |

> ★ **핀 확인 부탁드립니다.** `Y11 = PMOD JA1 1번 핀`이라는 대응은 ZedBoard 매뉴얼
> 기준이며 이 저장소에서 문서로 대조한 적이 없습니다. Vivado로 확인한 것은
> **"Y11은 뱅크 13의 범용 IO다"** 까지입니다 (`get_package_pins Y11` → `bank=13`,
> `IS_GENERAL_PURPOSE=1`). 실크스크린이나 ZedBoard master XDC로 한 번 대조할 것.

**확인할 것** :
1. `CAP_CNT`가 올라가는가 (신호가 들어오는가)
2. 타임스탬프 **간격**이 STM32가 내보낸 주기와 맞는가 ← 이게 진짜 검증이다
3. `DROP_CNT` — Mode 2에서 처음으로 데드타임 손실이 의미를 갖는다
